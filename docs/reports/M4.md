按你给的范围：

1. **真实 Firefox 的 AudioContext 与 WHEP**：
   - AudioContext：三个片段播放时 AudioContext 都是时钟（没有 `audioClockUnavailable`），暂停 6 s 后挂起、再播放恢复，见验收项 4。Linux 无头 Firefox 的 `resume()` 不返回只是那个环境的问题。
   - WHEP：视频每秒 25 帧，音轨 RMS 0.062（440 Hz 测试音）。为了在 Firefox 上跑通改了两处测试（产品代码不需要改），原因见 RESEARCH §1：
     - 自动化下的 Firefox 对直接从本地服务器加载的页面不启动 ICE 收集，`data:` 页面和经 Playwright 路由交付的页面都正常，根因没查清。用例在 Firefox 上把页面经路由交付。
     - Firefox 的主机候选默认是 mDNS 名（`.local`），本地 werift 夹具解析不了。Firefox 项目关掉了这个混淆。
   - 结果：WHEP 播放用例不再在 Firefox 上跳过，Linux 无头 Firefox 和 Windows 正式版都实际播放。
2. **多宫格 16 路，真 GPU**：Edge 的 WebCodecs 在这台机器上没有 HEVC 硬解（`isConfigSupported(hvc1, prefer-hardware)` 为 false，Windows Server 一般不带 HEVC 扩展），所以 HEVC 仍走 WASM。为了得到「硬解」数据，加了同一个帧号片段的 720p H.264 版（`frames/h264-720p.mp4`，`OTTER_BENCH_SRC`），用 WebCodecs 解码。整个浏览器的 CPU 按进程类型取自 CDP `SystemInfo.getProcessInfo`，除以 16 得到每路。

   | 16 × 720p，Edge，RTX 3080 | 解码 | 每路 CPU（整个浏览器 ÷ 16，单核 %） | 进程合计（单核 %） | 每路 10 s 内播放 | 丢帧（时钟 + 画布未显示） | 主线程 |
   |---|---|---|---|---|---|---|
   | HEVC | WASM，4 个 Worker（解码池里每路 19.2–19.8%） | 24.7 | 渲染进程 348、GPU 31、浏览器 16 | 9.88–10.16 s | 每路 0 | 600 rAF，> 20 ms 0 次，最长 19 ms，长任务 0 |
   | H.264 | WebCodecs | 4.4 | 渲染进程 19、GPU 38、浏览器 13 | 9.86–10.13 s | 每路 0 | 600 rAF，> 20 ms 0 次，最长 18 ms，长任务 0 |

   2026-10-28 复测（新实例 inst-01m4skyh…，同为 RTX 3080 / Server 2022，Edge 153）：HEVC（WASM）丢帧 0、主线程最长 18 ms、浏览器每路 24.9% 单核；H.264（硬解）丢帧 0、最长 42 ms、每路 5.5% 单核；两组用例都因第 1 路 `audioClockUnavailable` 失败（有界面 Edge 的自动播放策略，见 M6.md 失败表 F1）。
   原始数据：`docs/reports/m4/multiview-16-hevc-real-windows-edge.json`、`multiview-16-h264-real-windows-edge.json`。H.264 那一行是否真的走了硬件解码，测试没有单独断言；从渲染进程只占 19%（软解 16 路 720p 需要数个核）推断是硬解。本机无头 Chrome 跑同样的 H.264 时整个浏览器每路 17.3%，GPU 进程（SwiftShader）60%，画布有 260 帧左右被新帧覆盖；真 GPU 上为 0。
3. **WebKit 色彩管理**：按你的要求不在这台机器上验 WebKit，结论来自 CI 的 WebKit 数据和这台机器上的 Edge / Firefox，写进 ADR-008 §6 与 RESEARCH §1：
   - 平台对 `<video>` 做色彩管理、对画面面不做，**不是 WebKit 独有**。真机 Edge（硬件视频通路）也这样：未打标签的 SD 视频，红色彩条在 `<video>` 里是 (248, 36, 0)，在 2D canvas 和 WebGL 里都是 (254, 0, 0)。WebKit 是 `<video>` 与 2D canvas 做、WebGL 不做。无头 Chrome、Linux 无头 Firefox 和 Windows Firefox 三条路径一致。
   - 原来的探测比较 2D canvas 与 WebGL，在 Edge 上探测不到这个差别，surfaces 用例因此在真机 Edge 上失败（平均差 12–13，离群像素 33%）。现在对每个画面面直接拟合到 `<video>` 的颜色映射：接近恒等就不拟合、阈值不变；不接近恒等的必须像色彩管理，平均差上限 12，离群像素上限 3% 不变。Edge 最差平均差 10.5、离群 2.0%；WebKit 离群 ≤ 0.34%。
   - 产品上的影响：同一路视频在 WebCodecs 画布（多宫格、HEVC 软解）和 `<video>` 上的红色有可见差别。修正（画面面按 `VideoFrame.colorSpace` 做转换）留在 HDR / 色彩管理批次。
4. **带音轨的公开 WHEP 源**：没找到能用的。
   - Eyevinn 示例（`wrtc-edge.lab.sto.eyevinn.technology:8443/whep/channel/sthlm` 等）从这台机器访问返回 502；Broadcast Box（`b.siobud.com/api/whep`）要流名作 Bearer（401）；SRS、OvenMediaEngine、Cloudflare、Ant Media 都没有公开的常驻 WHEP 地址。
   - 改为让本地夹具也发音轨（Opus 440 Hz）：在 Edge 和 Firefox 上用 AnalyserNode 量到接收流的 RMS 0.062，`<video>` 拿到一条视频轨、一条音频轨。这只证明有声音信号到达，我没有「听」。你如果有可用的公开源，我再手动播一次。
5. **Edge 上的 canvas PiP 与单标签出声**：都通过。canvas PiP 在 PiP 窗口里 1.5 s 收到 45 帧，进出时播放不中断；单标签出声的三个页面用例全部符合（后开的标签让先开的静音，暂停、关闭后不恢复，`audio-yield` 一次）。真机 Firefox 上这两项也通过（PiP 40 帧）。

真机上发现并修复的问题：

- PiP 用例在开始等待时就把「还没进入 PiP 的 inline」当成了结果（真机 Firefox 失败）。现在等请求结束：进入 PiP，或 `pending` 为空。
- 多宫格基准对 WebCodecs 的路也去读解码池的数字，出现负数，现在只对 WASM 的路读。
- WebDriver BiDi 的两处限制：`dblclick()` 不发 `dblclick` 事件；`emulateMedia({ reducedMotion })` 不生效。依赖这两点的两个用例在 `real-windows-firefox` 上跳过（RESEARCH §1）；真实用户的双击不受影响，Edge 上这两个用例照常通过。

## M4 → M5 交接：自研 CMAF-HLS 引擎开工前要确认的接口

M5 的引擎按 ADR-010：`format-hls` 内的按需块，外面包 `withAdapterFallback`，不支持的情况交 hls.js，PTS 不平移。下面五个接口逐个列出现状和要改的点；「建议」是我的方案，需要你确认。

### 1. Engine / EngineContext：分片引擎要不要加字段

现状（`packages/media/src/format.ts`）：

- `EngineContext`：`source`、`options`（`startTime`、`autoplay`、`quality`、`signal`）、`caps`、`backend`、`qoe`、`media`、`mms`、`allowCodecSwitch`、`cmcd?`。
- `Engine`：`formatId`、`tracks`、`latency?`、`mms`、`load()`、`selectQuality()`、可选的 `selectTextTrack`、`selectAudioTrack`、`seekToLive`、`thumbnails`，事件 `tracks-change`、`quality-change`、`latency-change`、`first-segment`、`bandwidth`、`text-cues`、`error`。
- `backend-mse` 只按 timeupdate 读 `engine.latency`，**不转发**引擎的 `latency-change`，所以引擎给出的目标延迟（`target`）到不了 session 和 QoE（hls.js 适配器发了 target 也一样丢掉）。
- 直播时进度条整体禁用（`ui-core` 里 `!s.live` 才可拖），状态里没有可拖范围。

要改的点：

- **不加 EngineContext 字段**。分片引擎需要的都已在 ctx 里：起播位置在 `options.startTime`，ABR 规则与 hls.js 回退通过 `createHlsFormat` 的选项传入，CMCD 在 `cmcd`。
- **Engine 加一个可选 `readonly targetLatency?: number`**，`backend-mse` 采样时一起读，并在 `latency-change` 里带上 `target`（对 hls.js 适配器同样生效）。改动约 5 行，不影响首屏。
- **可拖范围（直播 DVR）**：引擎内部调用 `mediaSource.setLiveSeekableRange`，元素的 `seekable` 就对了，不需要新接口。但界面要能拖直播窗口，需要 `PlaybackSnapshot` 增加 `seekableStart` / `seekableEnd`，并让时间条在直播时使用。建议：M5 首批只做 `setLiveSeekableRange` 和「回到直播」，直播窗口拖动留到 M5 的直播 UI 一项再定。

### 2. MSE sink：分片账本、timestampOffset、abort()

现状（`packages/engine-pipeline/src/mse-sink.ts`，208 行）：

- 每个 SourceBuffer 一个串行队列，用 `segments` 模式；codec 变化时 `changeType`。
- `QuotaExceededError` 时先清后缓冲再重试一次；`evict(currentTime)` 按秒清后缓冲；`clear()` 是 `remove(0, ∞)`；`endOfStream()` 等队列排空。
- MMS 的 `streaming` / `whenStreaming()` 已有。
- 只知道时间区间（`buffered(type)`），不知道里面是哪些分片。

要改的点：

- **分片账本**（必需）：`append(type, data, seg?: { id, start, end, level })`。追加成功后记一条，`evict` / `clear` / 浏览器自行驱逐后按 `buffered` 修剪；查询接口 `segments(type)`。用途：
  - 判断哪些分片已经在缓冲里（`getSegmentsToLoad` 需要）；
  - 降档时保留更高码率的已缓冲分片（SPF `planTasks` 的做法）；
  - `isLastSegmentAppended`（`endOfStream` 的时机）。

  估计 50–70 行，`format-mp4-range` 不用这个参数，行为不变。
- **timestampOffset**：ADR-010 定了 PTS 不平移，带 `EXT-X-DISCONTINUITY` 的流交 hls.js，所以 M5 首批**不需要**。建议不加。如果以后要加，必须作为队列里的一个操作（只能在 SourceBuffer 不 `updating` 时设置）。
- **abort()**（必需）：seek 或切档时中断正在进行的追加。做法：清掉该队列里未执行的操作（让它们的 Promise 以 `AbortError` 结束），当前操作在 `updating` 时调用 `sourceBuffer.abort()`，然后把解析器状态视为重置（下一段之前要重新追加 init）。`append-segment.ts`（SPF）在中断流式追加后同样调用 `abort()`。现在 `clear()` 只能排在正在进行的追加之后。
- 另外：`mediaSource` 已暴露，`setLiveSeekableRange` 由引擎直接调用，sink 不需要包一层。

### 3. withAdapterFallback 的触发条件

现状（`packages/engine-pipeline/src/fallback.ts`，81 行，FLV / TS 在用）：

- 只在 `load()` 期间：主引擎 `load()` 抛出 `OtterError` 时，如果错误类型是 `network`、或 details 是 `unsupportedSource`，就原样抛出（不回退）；其他情况销毁主引擎，换适配器重建一次，发非致命 `pipelineFallback`，再 `load()`。
- `load()` 之后的运行时错误只转发，不回退：会作为致命错误进 session，接着是同一后端重试，再走降级链（MSE 之后是 native）。
- 非 `OtterError` 的异常原样抛出。

要改的点：

- **「不支持」要能触发回退**。ADR-010 要求解析阶段发现 DISCONTINUITY、AES-128、TS 分片、LL-HLS part、I-frame 清单就交给 hls.js。但现在 `unsupportedSource` 恰好被排除在回退之外（它表示「这个格式放不了这个源」，比如 Blob 给了 hls.js）。建议新增 details `ownEngineUnsupported`（`type: 'media'`，`reason` 写进 message），`withAdapterFallback` 对它回退，并把原因记进 `router.explain()`。这需要一个新的 `route-detail` 通道：引擎事件里没有这个事件，要么 `Engine` 加 `route-detail`，要么把原因写在 `pipelineFallback` 的 message 里由 backend-mse 转成 route 步骤。建议后者，不改 Engine 契约。
- **运行时回退要不要做**：自研引擎播放中出错（例如追加失败），现在会走 session 的降级链到 native。iPhone 上 native 能播 HLS，桌面 Chrome 上 native 不行，结果是报错而不是交给 hls.js。建议 M5 加「运行时回退一次」：从当前位置用 hls.js 重建（与 FLV / TS 共用），发 `pipelineFallback`；网络错误仍不回退。
- **命名**：`pipelineFallback`、message 里的「own pipeline」「the adapter」对 HLS 也适用，保留不改；QoE 消费方不用改。

### 4. ABR driver：sampleDownload / decide 的调用点

现状（`packages/pipeline/src/abr/driver.ts`）：`createAbrDriver()` 持有 EWMA 估计器和规则栈。各调用方：

| 调用方 | `sampleDownload` | `decide` | `segmentAppended` / `applied` / `reset` |
|---|---|---|---|
| hls.js 适配器 | FRAG_LOADED，用 hls.js 的 loading stats（含 ttfb） | hls.js 的 `nextAutoLevel` 钩子 | 有 |
| Shaka 适配器 | AbrManager 的 `segmentDownloaded`（小于下限的样本丢弃） | AbrManager 的 `chooseVariant` | 有 |
| mp4-range | 每个 Range 请求结束（不含 ttfb） | 每个 step 之前（`target()`） | `segmentAppended` 每个视频分片；`applied` 切档后 |
| WebCodecs 后端 | demuxer 的下载事件（含 ttfb） | 每次决定下一段读哪个档位 | `applied` 切档后 |

自研引擎的调用点（建议）：

- `sampleDownload(ms, bytes, ttfbMs)`：每个**媒体分片**下载完成时调用，不含 init 分片和播放列表（太小，会把估计拉低）。时间从请求发出到 body 读完，`ttfbMs` 取响应头到达时刻。每次之后发 `bandwidth` 事件（`canEstimate` 之后）。
- `decide(snapshot)`：在调度器选**下一个视频分片**之前调用。
  - `bufferLevel` 取视频 SourceBuffer 的前向缓冲（不是元素的 `buffered`，那是音视频的交集）；
  - `segmentDuration` 取 `EXT-X-TARGETDURATION`；
  - `live`、`lowLatency` 取自播放列表；
  - `bufferTarget` 取前向缓冲目标。

  音频档位不经过 ABR。
- `segmentAppended()`：每个视频分片追加成功后调用；`applied(level)`：手动切档或实际切到新档位时调用；`reset()`：seek 时调用。
- 切档点：新档位的第一个分片从不早于「时钟 + 1 s」的分片边界开始（RESEARCH §1，`SWITCH_LEAD_S` 的教训对 MSE 同样适用）。
- 接口本身**不用改**。

### 5. LiveController：目标延迟从 HOLD-BACK 取

现状（`packages/pipeline/src/live/controller.ts`）：

- `createLiveController({ targetLatency, catchUpRate })`：目标延迟在创建时固定，默认 1 s，最小 0.3 s。超过目标 + 1 s 就 seek，超过目标 + 0.4 s 就加速（mpegts.js 的规则）。
- 延迟按「`buffered` 末尾 − 播放位置」算。
- FLV / TS 管线由 `createFlvFormat({ targetLatency })` 传入。

要改的点：

- **目标延迟来源**：HLS 的目标在解析媒体播放列表后才知道。取 `EXT-X-SERVER-CONTROL:HOLD-BACK`，没有时取 3 × `TARGETDURATION`（SPF `reload-policy.ts` 的规则，RFC 8216bis 的建议值）；宿主可以用 `createHlsFormat({ targetLatency })` 覆盖。不改接口也能做：引擎在第一个媒体播放列表到手后再创建 LiveController。但切换 variant 后 TARGETDURATION 可能变，所以建议加 `setTargetLatency(s)`（约 10 行，重算 config）。
- **延迟的定义**：LiveController 用「缓冲末尾 − 播放位置」，对 FLV 长连接这就是到直播边缘的距离。对 HLS 不是：缓冲末尾是最后追加的分片的结尾，比播放列表的直播边缘最多落后一个刷新周期加前向缓冲的空位。建议 `LiveSample` 加可选 `edge?: number`（直播边缘的媒体时间：最后一个分片的结尾，或按 PDT 推算），有它时 `chaseLatency` / `syncRate` / `seekToLive` 用它代替缓冲末尾；FLV / TS 不传，行为不变。
- **起播位置**：`edge − HOLD-BACK`，由引擎在第一次 seek 时设置，不经过 LiveController。
- **对外报告**：`Engine.latency` 返回 `edge − currentTime`，加上第 1 条的 `targetLatency`，stats 面板和「回到直播」就有正确的目标值。
- **体积**：LiveController 0.69 KB 已在 Q3 估算的 13–14.5 KB（含直播）之内。

### 三级降级（人为禁用硬解）

播放器外壳 `?prefer=webcodecs&hw=off&wasm=fail` 播本地 H.264 HLS（`e2e/fallback.spec.ts`）：`hw=off` 让 WebCodecs 解码器不接视频（`disableVideo`，等同没有该编码的解码器），`wasm=fail` 让 WASM 解码器的文件缺失。每个环境都按同一顺序降级：

| 环境 | 路径（`router.explain()`） | QoE `error` 事件（剩余步骤） |
|---|---|---|
| desktop Chrome / Firefox / Android 仿真（本机），desktop Safari（CI） | webcodecs selected → webcodecs failed（codecUnsupported）→ wasm selected → wasm failed（workerDecoderFailed）→ mse selected，播放 | codecUnsupported（wasm、mse[、native]），workerDecoderFailed（mse[、native]） |

每次决策另有一条 `route` QoE 事件。只禁用硬解（`?hw=off`）时，HEVC HLS 落在 WASM（Chrome、Android 仿真）；Firefox、Safari 的 MSE 本身能播 HEVC，不经过 WebCodecs。

### Q3 材料：自研 CMAF-HLS 引擎与 SPF

> 结案（2026-10-21）：方案 A，见 ADR-010；体积口径改为两条独立门禁（自有代码不变；引擎块点播 ≤ 12 KB、含直播 ≤ 15 KB）。

拟采用的方向（由项目负责人据此结案）：M5 的 CMAF-HLS 引擎独立实现，不依赖 SPF 运行时，体积对标 SPF。本节回答「SPF 哪些文件能按 L3 拷、哪些要改写、Otter 已有代码能用多少、体积大概多少」。

- SPF 来源：`videojs/video.js@92be7bdd72c8782348ebafc765a23cf8d8cba004` 的 `packages/spf`（`@videojs/spf` 10.1.0）。下文路径都相对 `packages/spf/src/`。
- 行数：`wc -l`，含注释，不含 `tests/`。SPF 非测试源码共 21,542 行：`core` 1,775、`media` 6,436、`network` 600、`playback` 12,501。
- 体积口径：esbuild 0.28.2 打包，minify，ESM，es2022，zlib gzip 默认级别；1 KB = 1000 B（与 size-limit 一致）。SPF 自己的 `scripts/measure-size.js` 用 KiB（1024 B）。

#### 要点

1. SPF 分两层。`media/`、`network/` 下多数文件是纯函数，可以按 L3 拷；`playback/` 和 `core/` 建立在 SPF 自己的 signals / actor / reactor / composition 运行时上，只能改写（L4），个别函数可以抽出来。
2. 可拷的主要是 m3u8 解析（约 1,200 行，带 2,100 多行测试）、前后缓冲计划、直播重载节奏、fMP4 `tfdt` 读取。MSE 操作、带宽估计、ABR 与 Otter 已有代码重叠，不需要拷。
3. Otter 已有 MSE sink、ABR 规则栈、LiveController、适配器回退，可以原样复用。缺的是播放列表加载与刷新、分片调度器、分片账本、直播可拖范围。`format-mp4-range` 的引擎是调度器最接近的样板。
4. 「SPF 约 12 KB」在当前 SPF 里找不到出处。实测 SPF 的 HLS 视频引擎约 28 KB gzip，还不含 `signal-polyfill`；SPF 脚本自己的目标是 20 KiB。Otter 按上面的拼法估计 10–14 KB。
5. 体积门禁有冲突，需要负责人先定：ADR-009 写的是「含引擎口径简单点播 < 30KB」，而短视频场景的自有代码现在是 25.88 KB，引擎块只剩约 4.1 KB。

还缺、需要新写的部分：

1. 播放列表加载与刷新：拉主清单和媒体清单，直播按 `reload-policy` 定时重载。解析器和重载间隔可以拷，加载循环要写。
2. 分片调度器：用 `getSegmentsToLoad` 决定拉哪些分片；切换 init；处理 seek、切档、结束（`isLastSegmentAppended`）；配一个分片账本。
3. variant 过滤：按 MSE `isTypeSupported` 或 Otter 的能力探测去掉放不了的 codec，再交给 ABR。
4. 轨道映射：把 variant 和音轨映射成 Otter `TrackList`，发 `quality-change`，实现 `selectAudioTrack`。
5. 直播：起播位置、`setLiveSeekableRange`、接 LiveController。
6. 时间线：决定是否用 `timestampOffset` 把非零 PTS 平移到 0（SPF 平移，Otter 现有引擎不平移）。
7. 不支持的情况交回 hls.js。SPF 也不覆盖这些：`EXT-X-DISCONTINUITY`、I-frame 清单（Otter 的 hls.js 适配器用它做缩略图）、LL-HLS part、AES-128（SPF 遇到非 DRM 的 `EXT-X-KEY` 报 `SVTA_UNSUPPORTED_ENCRYPTION_METHOD`）、TS 分片、内容导向。建议解析器遇到这些就报「不支持」，由 format 选 hls.js。

工作量粗估：拷入约 1,500 行（大部分是解析器），新写 500–700 行（参照 mp4-range 引擎的 372 行，再加播放列表循环和直播部分）。这是估计，没有原型验证。

#### 5. 建议与取舍（由负责人决定）

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A | L3 拷 SPF 的解析器、缓冲计划、重载策略、`tfdt` 读取；MSE sink、ABR、LiveController、回退用 Otter 已有的；调度器参照 mp4-range 新写 | 符合「独立实现」；运行时只有 Otter 自己的；估计 10–14 KB；解析器带 100 个左右现成测试 | 拷来的约 1,500 行要跟上游（CHANGELOG 记了 42 个版本，2026-10 一个月内发了 10.0.0、10.0.1、10.1.0）；要把 CMAF-HAM 类型改成 Otter 的；`DISCONTINUITY`、AES-128 等不支持的情况要回退 hls.js |
| B | 完全自写，只借设计（L4） | 数据模型从一开始就是 Otter 的 | m3u8 的边角情况（BYTERANGE 续接、PDT 插值、直播窗口接续）要自己踩一遍；测试也要自己写 |
| C | L1 依赖 `@videojs/spf` | 现成，功能更全（DRM、字幕、多 CDN） | 不符合 Q3 前提；约 28 KB 加 `signal-polyfill`；SPF 自己管 MediaSource 和错误码，和 Otter 的 backend、ABR、QoE 分层冲突 |

建议 A。理由：可拷的部分正好是纯函数、容易出错、带测试的那一层；和运行时绑定的部分，Otter 已经有等价物，或者 mp4-range 已经是同样结构的样板。

需要负责人定的事：

1. 简单点播「含引擎 < 30KB」怎么处理：首屏自有代码再减 6–10 KB；或者改为只对引擎块单独设预算（例如 ≤ 12 KB）；或者简单点播的 HLS 默认走 native / mp4-range，自研引擎只承担长视频点播。

3. 非零 PTS 用不用 `timestampOffset` 平移到 0。
4. 引擎放在哪：新包，还是 `format-hls` 内的按需块。
5. SPEC §8 的「对标 SPF 12KB」是否改成实测值。
