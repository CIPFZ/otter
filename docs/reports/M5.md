### 引擎做了什么

- **结构**：
  - 每个 SourceBuffer 一条加载线：视频（可能带复用的音频），或单独的音频 rendition。
  - 每条线按 SPF 的前向缓冲计划取下一个分片，追加后记进 sink 的分片账本。
  - PTS 不平移：媒体时间 = 播放列表时间 + 第一个分片 `tfdt` 得到的偏移。
- **切档**：
  - ABR 切档不清缓冲，从已缓冲的末尾接上。
  - 手动切档像 hls.js 一样：清掉至少 1 s 之后、从分片边界开始的已缓冲视频，从那里按新档位重新加载。
- **直播**（单独的块）：
  - 按 SPF 的重载节奏刷新播放列表，换档时新 rendition 按 media sequence 对齐到当前时间线。
  - `setLiveSeekableRange` 维持可拖范围。
  - LiveController 以播放列表边缘为基准，目标为 HOLD-BACK（缺省 3 × TARGETDURATION）；支持回到直播。
- **字幕**（打开时才加载的块）：
  - 加载播放头附近的 WebVTT 分片。
  - `X-TIMESTAMP-MAP` 按 MPEGTS 映射到媒体时钟，与 hls.js 在同一夹具上的出现时刻一致（七个时间点逐一核对）。
- **ABR**：精简规则栈（Throughput + InsufficientBuffer），每个媒体分片下载完采样。
- **交给 hls.js 的流**：加载时发现以下任一项即报 `ownEngineUnsupported`，由 `withAdapterFallback` 交给 hls.js，原因写进 `router.explain()`（例如 `own engine does not support this stream: EXT-X-KEY; using the adapter`）。
  - ADR-010 的五类：`EXT-X-DISCONTINUITY`、`EXT-X-KEY` / `EXT-X-SESSION-KEY`、TS 分片、LL-HLS part（`EXT-X-PART`、`PART-INF`、`PART-HOLD-BACK`）、I-frame 清单。
  - 另外四种：`EXT-X-GAP`、`CLOSED-CAPTIONS` 渲染（引擎还不提取 608）、variant 没有 `CODECS`、没有多码率主清单。

### 偏离与说明

- **点播门禁不含字幕块**：「点播 ≤ 12 KB」量每次点播都会加载的引擎块；字幕块只在打开 WebVTT 字幕时加载，算进「全部块 ≤ 15 KB」。连字幕块一起算，点播约 12.9 KB。
- **ABR 用精简规则栈**：没有 BOLA，为了点播块进 12 KB（完整规则栈约 3.0 KB，精简约 1.7 KB）；hls.js 适配器等仍用完整规则栈。记在 ADR-010 §3。
- **拷入代码的本地改动**：去掉了 SPF 媒体清单解析器里的诊断 `console.warn`，约省 200 B，行为不变（UPSTREAM.json）。
- **交给 hls.js 的不止五类**：另有 `EXT-X-GAP`、`CLOSED-CAPTIONS`、无 `CODECS`、无主清单四种，避免静默丢失字幕或播错。
- **WebKit 上发现并修复的两个问题**：
  - ManagedMediaSource 需要先关掉远程播放才会打开（`dfc46de`）。
  - 手动切档原先在缓冲已满时不生效（`ba3008f`）。

### 验收基准（自研引擎对 hls.js）

方法：`e2e/bench-hls.spec.ts`（`OTTER_BENCH=1`），本机 16 核，无头 Chrome 与 Firefox，同一台机器、同一个本地源。

- **次数与顺序**：每组每个引擎 10 次（直播 5 次），两个引擎交替先后，每次一个新的浏览器上下文。
- **链路**：媒体走 `e2e/throttle.ts`，服务端按会话限速，同一页面的分片、播放列表、init 请求共享带宽：不限速、约 3 Mbps、约 1 Mbps。
- **短视频**：`hls-fmp4`，8 s，360p / 180p 两档，播 10 s。
- **长视频**：`bench/ladder`，60 s，720p / 480p / 360p，峰值 2.8 / 1.4 / 0.77 Mbps，含音频，播 30 s。
- **TTFF** 取会话 QoE（load 到首帧）。**rebuffer** 是起播之后的 `waiting`。**切档**是起播之后的 `quality-switch` 次数。
- **直播**：本地直播夹具，HOLD-BACK 6 s。墙钟延迟 = 源端的实时直播点 − 画面里的帧号（30 s 循环内取模），分别取起播 1 s 后、稳定后（15–25 s 的中位数）、暂停 8 s 再回到直播 3 s 后。
- **原始数据**：`docs/reports/m5/bench-hls-*.json`（已被重跑结果覆盖）。
- **重跑时新增**：直播每次在稳定段的 10 个采样点同时读引擎报告的延迟（`state.latency`），记「引擎报告 − 墙钟」。

#### 第一次运行（2026-10-22，`31337a3` 之前的引擎）

TTFF 全部更快，rebuffer 大多持平；三项比 hls.js 差，按负责人要求先报不修：

1. **Chrome 长视频 1 Mbps 的 rebuffer 总时长**：自研 3.16 s，hls.js 0.67 s。原因是没有「下载中途放弃」规则，720p 分片硬下完 5 s 才降档。
2. **短视频片尾多一次切档**：已无分片可加载、缓冲见底时，InsufficientBuffer 判成「缓冲空」，多降了一次。
3. **直播延迟高 0.1–0.6 s**：根因是引擎报告的延迟比墙钟少约 3 s（Chrome：报告 4.51 s，墙钟 7.4 s）。引擎以为自己已在 HOLD-BACK 之前，所以不追。

#### 修复（2026-10-23，`a0cf11b`、`2f56fb0`、`ae8b08f` 及本节提交）

1. **下载中途放弃**：
   - 照 hls.js `AbrController._abandonRulesCheck` 与 `getTimeToLoadFrag` 按 L3 拷入（`packages/format-hls/src/vendor/hls.js/abandon.ts`，改成纯函数，本地改动见 UPSTREAM.json）。
   - 外层是按需块 `src/own/abandon.ts`，只在多档位清单时加载。自动档下逐块读视频分片的响应体，每 100 ms 估算剩余下载时间；超过前向缓冲能撑的时间就取消请求，把已下载部分计入带宽样本，改下剩余缓冲内能下完的最高档位。
   - 放弃动作发非致命 QoE 错误 `segmentAbandoned`，带原因（例如 `abandon: video-0 segment needs 5.3 s, 1.9 s buffered -> video-2 (1.6 s)`）；同一句写进 `router.explain()`。
2. **片尾多切档**：
   - 没有分片可加载时不调 `decide()`；seek 到片尾附近同样不调。e2e 覆盖：播到结尾，再 seek 到结尾前 1.5 s 播完，切档 0 次。
   - 随后 WebKit CI 暴露两个连带问题，都已修复：
     - 片尾的手动切档也被跳过了，而 hls.js 会立即切。现在只有 ABR 决定等分片，手动选择立即生效（`2f56fb0`）。
     - ManagedMediaSource 在片尾 `endstreaming` 后，加载线在等待 `startstreaming` 时挡住了之后做出的手动选择。现在等待期间每 200 ms 重新检查一次。本机用一个模拟 MMS（在 `sourceended` 时发 `endstreaming`）复现了 WebKit 的失败并验证修复，这个模拟已作为 e2e 常驻。
3. **直播边缘**：
   - edge 改为「最近一次重载的播放列表末尾 + 该响应到达后经过的墙钟时间」（上限 3 个 TARGETDURATION，防止重载卡住时无限外推）。
   - 有 `EXT-X-PROGRAM-DATE-TIME` 时优先用它：edge = 最新分片起点 + 自其采集时刻起的墙钟时间。
   - 起播位置、`state.latency`、LiveController 采样、回到直播都用修正后的 edge；LiveController 的不调速区间保留。
   - 夹具的 PDT 原先比实际采集时刻早一个窗口，已改成与 `/live-hls/clock` 一致。e2e 校验报告延迟与墙钟之差 < 0.5 s。

### 结论

- **更好**：
  - TTFF 两种浏览器、两个场景、三种链路都更快：不限速时 49–80 ms 对 123–182 ms；限速时快 0.7–22%（长视频 1 Mbps 差距最小，链路本身是瓶颈）。
  - 直播延迟低约 1 s：自研稳定在 HOLD-BACK（6 s）附近，hls.js 在 6.8–7.1 s，且各次之间波动大（p90 7.6 s）。
  - 引擎报告的延迟准确：与墙钟差 ≤ 0.09 s；hls.js 的报告值比墙钟低约 1 s，最大偏差 1.8 s。
  - 长视频 1 Mbps 的 rebuffer 总时长短于 hls.js：538 ms 对 665 ms。
  - 长视频 3 Mbps 在 Chrome 上切档更少：1 次对 2 次。
- **持平**：其余组的 rebuffer 两边都是 0；起播和结束清晰度一致；Firefox 上的切档次数相同。
- **更差**：本次重跑没有。

### 偏离与说明（本次）

- **放弃块的体积口径**（需要负责人定）：放弃块 1.1 KB，目前**不计入**「含直播 ≤ 15 KB」门禁，只单列报告。

### DVR 时间条（`b3f197d`，修正 `5825709`）

- **时间条**：直播时以 `[seekableStart, seekableEnd]` 为范围，窗口不足 1 s 时禁用。预览卡显示「−14.0 s」，读屏读「Behind live 14 seconds」。直播部分都在 `live-view` 按需块里，首屏 25.98 KB（此前 25.83 KB，上限 30 KB）。
- **直播标签**：「直播」后跟落后秒数（`−6.0 s`），取引擎修正后的 edge。「回到直播」改为比引擎目标延迟（新增 `state.targetLatency`，HLS 为 HOLD-BACK）多落后 3 s 以上才出现：原来固定 3 s，在 HOLD-BACK 6 s 的流上会一直显示。
- **延迟采样**：backend-mse 从每秒 1 次改为 4 次。原来暂停时显示值最多滞后 1 s，过不了 ±0.5 s。
- **FLV / TS 管线**：可拖窗口就是已缓冲范围（一条长连接，丢掉的过去取不回）。
- **e2e**（`e2e/dvr.spec.ts`，Chrome / Firefox / Android 仿真）：
  - 时间条范围等于可拖窗口；
  - 在目标延迟处两次、拖到窗口起点后一次，显示的落后秒数与画面帧号算出的墙钟延迟之差 < 0.5 s；
  - 「回到直播」一次点击回到目标并继续播放；
  - FLV 的窗口等于已缓冲范围。

- **修正（`5825709`，CI WebKit 暴露）**：
  - **拖动后继续播放会被拉回**：LiveController 沿用 mpegts.js 的追帧规则，拖到窗口靠前处后一播放就被追回目标延迟；拖到已缓冲范围之前时，起播卡顿规则把播放头跳到缓冲起点。现在控制器区分自己的 seek 和用户的 seek：可播放之后的用户 seek 暂停追帧、倍速同步和卡顿跳转，倍速回到 1，直到「回到直播」或播放头回到目标 + 1 s 以内。HLS 有 edge，引擎会补载，卡顿跳转只用于起播。FLV / TS 同样适用。e2e 加一步：拖动后播放 3 s，延迟变化 < 1 s、倍速为 1。
  - **e2e 读帧号的方法**：原来先截图再读时钟，WebKit 上截图要 0.5–0.9 s，播放中的墙钟延迟被多算这么多（CI：显示 6.1 s，墙钟 6.72 s）。现在在页面里把 `<video>` 画到画布上读帧号，与落后秒数、时钟在同一时刻读取。
  - **采样节流**：0.8 × 250 ms，定时器略早触发时不再整拍跳过。

### 画布 SDR 色彩管理（`a14abe6`）

- **先测清楚平台在做什么**（Windows Edge 真机，RESEARCH §1）：
  - Chromium 给 `<video>` 做色彩管理的条件是 **GPU 合成**，不是硬件解码。关掉硬件解码、关掉 DirectComposition 叠加层后照样转换；`--disable-gpu`（软件合成，与无头 Chrome 相同）后不转换。
  - 转换的算法：sRGB 曲线线性化 → SMPTE 170M 到 BT.709 原色矩阵 → sRGB 曲线编码。六根彩条逐一复现到个位（红 253,0,1 → 246,36,0）。
  - 未打标签的 SD 帧，各浏览器给出的 `VideoFrame.colorSpace` 不一样：
    - Chrome 的 `new VideoFrame(video)` 报 `smpte170m`，而 WebCodecs 解码器的输出全为 null。
    - WebKit 报 `primaries smpte170m / matrix bt470bg`。
    - Firefox 的帧是 RGB，没有标签，或标为 `bt709`。
- **做法**（`packages/surface/src/color.ts`）：
  - **何时转换**：只在平台本身给 `<video>` 做色彩管理时转换，否则画面面反而与 `<video>` 不一致。
    - 依据是 WebGL 渲染器名：SwiftShader / llvmpipe 等软件渲染不转换。
    - 绘制路径若自己已经转换就跳过。判断方法：用一个打了 SMPTE 170M 标签的红色小帧探测，WebKit 的 2D canvas 就属于这种。
  - **原色**：
    - 有标签用标签。
    - YUV 帧没有标签时按高度推定：< 720 行用 SMPTE 170M，否则用 BT.709。
    - RGB 帧没有标签时视为已在显示色域。
    - 只转 SD 原色（SMPTE 170M、BT.470BG）；BT.709 与 sRGB 原色相同，不用转。
  - **GPUSurface**：在 fragment shader 的取样函数里转换，锐化取的邻点也一样转换。I420 的 YUV → RGB 按 BT.601 / 709、limited / full range 由 Kr、Kb 计算；`I420Frame` 增加 `fullRange`、`primaries` 两个字段。
  - **CanvasSurface**：`ctx.filter` 引用一个 `linearRGB` 的 SVG `feColorMatrix`。
- **e2e**：`e2e/surfaces.spec.ts` 删掉颜色映射拟合和放宽的平均差上限。三种 Surface 直接逐像素比较，阈值回到原来的平均差 < 6、差值 > 40 的像素 < 3%。

### 第二批遗留三件事

1. **滤镜色差**（`d6a009a`，限时一停，一次降下来，保留）：
   - **先核对平台的做法**：本机 147 个颜色、四组滤镜。CSS 简写函数在 Chromium 和 Firefox 上都是：每个函数一个滤镜原语，每一步之后截断到 0–1，在 sRGB 里计算，**不线性化**。三种模型和实测的平均差：
     - 逐步截断：0.17–1.26
     - 合成一个矩阵、只在最后截断：4–5
     - 线性化：19–20
   - **原因**：shader 原来把三步合成一个矩阵、只在最后截断。被亮度截断的亮像素，又被对比度拉了回来。
   - **改法**：只用简写函数时，shader 按非中性的函数逐步计算、逐步截断，最多 3 步。用到色温或锐化时走 SVG 滤镜，那是一个 feColorMatrix，仍然只在最后截断。
   - **结果**：「亮度 / 对比度 / 饱和度」这组在 GPU 画面上：
     - CI WebKit 从 5.2 降到 1.2–1.3（全部组最差 1.27）。
     - 本机 Chrome 从 1.8 降到 0.0；Android 仿真从 2.2 降到 0.5。
     - Windows Edge 未测：真机不可用，见「偏离或疑问」。
   - 记进 ADR-008 §6。
2. **AudioContext 恢复**（`375d24e`、`f86b630`）：
   - **按要求改**：
     - resume 之后 `performance.now()` 作备用时钟，宽限 3 s。resume 完成时无缝切回 AudioContext 时钟（媒体时间接上），并撤回备用状态。
     - 只有 resume 明确失败，或 3 s 仍未完成，才报 `audioClockUnavailable`；消息里带原因。
     - 单测覆盖「resume 慢但成功」（2.5 s 内完成）和「宽限过后才完成」。ADR-008 §2 同步。
   - **之后 CI WebKit 又出现一次**（`78ecb37`），按「再出现就停下定位」：
     - 定位方法：加了 50 ms 粒度的 AudioContext 轨迹，WebKit 上连续 5 次空闲挂起与恢复，其中 2 次复现。
     - 轨迹显示 context 恢复后时间正常前进，报的却是「AudioContext time frozen for 0.5 s」。

   - 现象：带 `EXT-X-MEDIA:TYPE=AUDIO,URI=…` 的流，视频先追加了数据后才建音频 SourceBuffer，Chromium 拒绝（QuotaExceededError）。引擎随即按运行时回退交给 hls.js，播放没断，偏好也都保留。
   - 为什么第一批没发现：第一批的夹具音频都是复用在视频里的。
   - 修法很直接：起播时所有 lane 的 init 一起建 SourceBuffer。本机验证可行，但点播块会到 12,026–12,036 B，超 12 KB 门禁约 30 B。
   - **需要定**：放宽点播门禁约 50 B；或者把这类流列为第六类交给 hls.js，同样超约 20 B；或者等 M6 体积收口一起做。在此之前，编码选择的 e2e 用只含视频的 `video.m3u8`，偏好 e2e 用完整清单（走回退）。
2. **WebKit 虚报 AV1 的处理方式**：按要求「结果进 `router.explain()`」以 decodingInfo 为准排序。但平台虚报时只能靠首帧前失败来发现，代价是起播多等约 3 s（卡顿判定）。可选：WebKit 上默认把 AV1 排到最后。现在没做，以免对真正支持 AV1 的 Mac（M3 起）不公平。
3. **Windows 真机不可用**：从 10-25 起 AGRT 网关对这台实例返回 503 `INSTANCE_NOT_RESOLVABLE: managed domain not found`，而实例 API 显示 RUNNING / READY；token 已按规定续过。所以：
   - 滤镜修正没在 Edge 上复测（原来 Edge 是 5.4，与 WebKit 同一原因）；
   - Edge 上的编码探测与偏好也没跑。
   - 请看一下这台实例。
4. **第 1 项比要求多做了两件**：
   - 平台虚报时剔除编码族（没有它，WebKit 上无法通过）；
   - 换片源和运行时回退保留倍速（偏好恢复倍速的前提）。

## 第三批第二停：独立音频修复、剔除缓存、DASH 音视频分离

### 做了什么

1. **自研 HLS 引擎直接播独立音频 rendition**（`74a720e`）：
   - 改法：首次追加媒体数据之前，所有加载线的 init 一起进 sink，各个 SourceBuffer 先建好。
   - 体积：一次尝试就够了。把只有直播用得到的 `align()` 移进直播块，点播块 11,995 → 11,938 B，12 KB 门禁不变；ADR-010 §3 已记。
   - e2e `hls-audio.spec.ts`（`codecs/h264-audio.m3u8`：H.264 + 英、法独立音频）：自研引擎直接播，不回退；切到法语后加载法语分片，播放继续。
   - 基准夹具 `generate-bench.sh` 改成英、法独立音频 rendition。本机冒烟一次，两个引擎都正常播放、无回退。
2. **编码族剔除缓存**（`6c70b66`、`c427f24`）：
   - 会话：剔除结果进 `state.codecExcluded`，同一页面之后的加载也不再尝试。
   - 偏好包：按「编码族 + UA」存在 `codec-failures` 这个 key（与用户偏好分开），30 天过期；下次访问起播前就排除，`router.explain()` 写「excluded: no picture on this device on <日期>, remembered until <日期>」。
   - e2e：第一次访问剔除并记下，第二次访问不再请求该族的 init、直接播下一族。Chrome / Android 用伪造的 HEVC，WebKit 用真实的 AV1。
3. **DASH 音视频分离（Shaka）**（`47291b3`、`3234024`）：
   - **音频不参与 ABR**：Otter AbrManager 只在当前音频流对应的视频 Representation 之间选择。新单测在旧代码上失败：旧代码会因带宽换到 64 kbps 的音频。
   - **切视频档不重拉音频**：手动选择当前正在播的 variant 时，Shaka 会强制清空所有流的缓冲（含音频）。e2e 抓到了这一点：音频分片被重复下载。现在这种情况只关 ABR、不切换。
   - **编码过滤**：Shaka 一侧补了 e2e，只加载排名最高、并且真正出画面的一族。
   - **同元素重载**：Shaka 的异步 `destroy()` 会摘掉新播放器的 MediaSource，WebKit 的 ManagedMediaSource 不会再打开，表现为剔除 AV1 后重载、之后不再发任何请求。现在先等旧播放器收尾再 attach；有在旧代码上失败的单测。
   - **夹具** `e2e/media/dash-av`：视频 H.264 三档（360p / 270p / 180p），英、法两个音频 AdaptationSet；`codecs.mpd` 另加 HEVC 与 AV1。§19「B 站式」场景改用它。
4. **WebKit 暴露、顺带修掉的**：
   - 判断「没有画面」改看元素实际解码的帧数（`getVideoPlaybackQuality`），不再看 `loadeddata`：WebKit 对解不出的 AV1 也会触发 `loadeddata`。
   - 首帧之前，引擎发起的、一直完成不了的 seek 也算卡顿：Shaka 跳空隙 seek 到 0.3 s 后卡住，原来不会报任何错误。
   - 播放中（时钟靠音频在走）连续 3 s 没有解码出任何视频帧也算卡顿。原来编码测试只看时钟走没走，WebKit DASH 上一度误报「AV1 在播」；两个编码 e2e 现在都断言解码帧数大于 0。
   - DVR 用例改为拖到分片边界：暂停的 WebKit 在 GOP 中间 seek 后显示的是关键帧，帧号读数会差约 1.7 s。

## 第四批：弹幕与水印（ADR-012）

### 做了什么

1. **弹幕核心、Canvas 2D、B 站 XML / JSON、设置页与偏好**（`865269a`）：
   - 新包 `@otter-player/danmaku`，按需加载，首屏不变。
   - 轨道分配从 `danmaku`（weizhenye v2.0.10）L3 拷贝，B 站 XML 解析从 CommentCoreLibrary L3 拷贝，各有 `UPSTREAM.json`。解析不用 DOM，Worker 里也能用。
   - 时间轴是媒体时间：位置是媒体时间的纯函数；跳变即 seek，重建舞台；暂停不重画；倍速跟随；页面隐藏时不画。
   - 设置菜单「弹幕」页（开关、不透明度、字号、速度、显示区域、密度、屏蔽类型），在二级按需块里；`@otter-player/preferences` 持久化。
2. **WebGL 批渲染与 OffscreenCanvas Worker**（`107dd33`，CI 基准步骤 `5a89d21`）：
   - WebGL：一张纹理图集、每帧一次 draw call。Worker：舞台画布交给 Worker，文字光栅化与绘制都在 Worker 里。两者都是按需块。
   - `renderer: 'auto'` 按最近 60 帧自动选择。阈值写在 ADR-012 §5 与 `POLICY` 里。每一步记成 `{candidate, outcome, reason}`，放在 `danmakuStatus.steps`，与 `router.explain()` 同形。
3. **蒙版弹幕与水印**（`7afa111`，之后按 CI 修正，见第 4 条）：
   - 蒙版两种输入，都是按需块（1.57 KB）：
     - SVG 帧：不用 DOM，`path d` 直接进 Path2D。
     - WebM alpha：隐藏的 `<video>` 逐帧 seek，用 rVFC 确认解出的是哪一帧。
   - 蒙版按**画面上正在显示的那一帧**取：`@otter-player/surface` 新增 `trackFrameTime`，经 `Overlay.tick(now, mediaTime, frameTime)` 传入。播放中再提前一个显示帧，加上渲染器自身的延迟。
   - 三种渲染器都支持擦除：Canvas 用 `destination-out`，WebGL 在着色器里乘系数，Worker 收到位图副本。
   - 水印 `createWatermark({mode})` 两种模式：
     - `static`：角标，文字或图片。
     - `moving`：canvas 文字，定时换到画面内的随机位置；被移除、隐藏或改透明度时立即还原。
   - 水印跟随全屏与 Document PiP（挂在容器里）。视频 PiP 用 `createPipComposite`：画面加水印合成到一个 canvas，经 `bindCanvasPip` 进 PiP 窗口。
   - ADR-012 §6、§7 已写。
4. **CI 暴露、已修的**：
   - **WebKit 的 rVFC**（`206de04`）：`expectedDisplayTime` 是「有新帧可用」的时间，早于上屏。外推的帧时间比画面超前 1–1.5 帧，蒙版超前 2 帧。改为外推结果不超过 `currentTime`。查过 WebKit 源码，已记 RESEARCH §1。
   - **Worker 延迟**（`1b773be`、`d95b1e2`）：
     - 原来量往返时间，回程消息在繁忙主线程上的排队也算进去了，WebKit 上提前量一度到 3.4 帧。
     - 现在量单程（投递到 Worker 画完，两边统一换算到 `timeOrigin`），取最近 15 帧的中位数，单次慢帧不影响。
   - **WebGL 在 WebKit 上更贵**（`0dd7b8a`）：
     - CI macOS 上 WebGL 主线程每帧 p50 6 ms / p95 19 ms，Canvas 2D 只有 1 ms。原策略进了 WebGL 就出不来。
     - 新规则：在 WebGL 上耗时 p90 仍 ≥ 4 ms 时，有 Worker 就换到 Worker，否则回到 Canvas 2D；WebGL 记为 `rejected: slower here`，本页不再尝试。ADR-012 §5 已补，有单测。
   - **WebM 状态时序**（`b22508d`）：原来在 alpha 检查之前就报了「webm: 30 fps」。WebKit 不解码 VP9 alpha，会在「就绪」和「拒绝」之间竞争。改为第一帧解出后才报就绪，10 s 内没有帧报 rejected。
   - **CI 通知丢失**（`aad4b5a`）：
     - Playwright 每次运行都会清空 `test-results/`。自从有了基准步骤（`5a89d21`），运行页只剩最后一步的通知，主套件的 dash-av、编码、水印等通知都丢了。
     - 现在每个 e2e 步骤都追加到同一个文件（`tooling/e2e-step.sh`），按主题合并成一条通知（`tooling/ci-notices.py`）。主套件失败时 @solo 与基准步骤照跑。
   - **其他**：
     - lib 构建清掉 `dist/assets` 里过时的 Worker 脚本，体积报告曾经量到旧文件。
     - 蒙版夹具每条弹幕改为 80 个 █：CI 的 Linux 字体把 █ 画得更窄，40 个铺不满画面。
     - `picture.spec` 改为等到 seek 后的那一帧再读：M5 第一批就记过的偶发，这次在 iPhone 仿真上连续两次出现。

2. **Firefox 的 WebGL / Worker 没有数字**：无头 Firefox 根本没有 WebGL。真实 Firefox 的数字可以等 Windows 实例恢复后，用 `real-windows-firefox` 补。
3. **WebKit 不支持 WebM alpha**：Safari 不解码 VP9 alpha，WebM 蒙版报 `rejected`，SVG 蒙版在 WebKit 上对齐正常。Safari 的透明视频是 HEVC with alpha（MOV），不在本批范围；要不要加第三种输入，请定。
4. **「≤ 1 帧」是按截图判的**：
   - 各引擎截图与真实上屏的关系不同：Chrome 的截图经过合成器，WebKit 的截图里覆盖层没有合成延迟。
   - 一个显示帧的提前量（16.7 ms）按 Chrome 定，WebKit 因此偏 +1、Chrome 的 Worker 偏 −1，都在 1 帧以内。
   - 真机上屏的误差要靠录屏或高速相机核对，本批没做。
5. **移动水印的还原**只防页面脚本与扩展的 DOM 改动，挡不住对整页做处理的截屏 / 录屏工具（ADR-012 代价一节已写）。
6. **Edge 待验项**（实例恢复后跑）：在前几批的六项之外，加上弹幕三种渲染器、蒙版对齐、水印 PiP 与全屏。
